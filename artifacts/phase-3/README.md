# Phase 3 — Standalone robot controller

This implementation lives in `followme.robotics`. It does not alter the existing environment CLI, vision worker, Phase 2 implementation, or camera-preview lifecycle. All commands default to fake hardware and Hold.

From the repository root, use the existing runtime environment:

```bash
source ./lerobot-env.sh
export PYTHONPATH="$PWD/src${PYTHONPATH:+:$PYTHONPATH}"
# Fake inspection: no serial or camera access.
python -m followme.robotics inspect --dry-run
# Synthetic A→B movement, recorded as simulated commands only.
python -m followme.robotics simulate --dry-run
# Acceptance tests and 100 real-thread randomized cancellation trials.
python scripts/check_phase3.py
```

Optional explicit physical **read-only** inspection:

```bash
python -m followme.robotics inspect --live-read
```

The read-only command checks device ownership, opens the follower bus, reads its calibration and positions, and closes without disabling torque. It never calls SDK `Robot.connect()` or changes motor settings. Avoid running it while another program owns the follower. It is not needed to pass Phase 3 and was not used during the implementation acceptance run.

## Integration contract

Construct `Controller(adapter, library, limits, clock, logger)` and `RobotWorker(controller)`. Start the worker; it binds adapter ownership and performs all I/O. Other threads may submit `TargetRequest` objects, call `set_mode`, `heartbeat`, `update_tracking`, `request_hold`, `stop_motion`, `reset`, and read immutable `status()` snapshots.

Only Follow with fresh tracking, a recent operator heartbeat, an armed adapter, and a recognized anchor permits a request. Requests are named poses, not joint dictionaries. At most one request is pending; active trajectories reject new requests. Reset is asynchronous: inspect subsequent status to see whether it succeeded.

`EventLog` stores bounded recent events and optionally writes JSONL. Request IDs, session IDs, source/feedback timestamps, requested/dispatched joints, backend, physical-command counts, arrival events, and cancellations are included. `RobotWorker.health()` detects a stale/dead worker without opening a second connection; the embedding application should poll it at least every 100 ms. Worker shutdown never releases another thread's live serial lock.

Readiness checks and controller defaults are defined in `config/robot.yaml`. The current production `config/safe_poses.yaml` is intentionally empty. Test poses are generated by `fake_library()` with backend `fake`, degree-valued arm joints, ±30° synthetic limits, and three-second directional paths; these are not measured hardware limits.

## Phase 4 handoff

The live pose file must have backend `live`, units `degrees`, five-joint measured `joint_limits`, `poses`, and `transitions`. Each pose has five-joint `joints`, `gripper_unchanged: true`, `approved: true`, and `hardware_sha256`. Transitions use keys such as `station_a->station_b` with `approved`, `hardware_sha256`, `waypoints`, and one `durations_s` entry per segment.

The library and each approval reference the SHA-256 of the passed Phase 0 `hardware.yaml`. Live arming checks its overall outcome and payload/workspace/stop/mount/location gates. Changes invalidate the revision. Both directions need independent approval. Existing calibration must match and the measured starting pose must be recognized uniquely.

No live-arm CLI is exposed in Phase 3. The supervised Phase 4 harness may request arming only after supplying those records. Arming refuses unsupported operating mode, seeds disabled arm-joint goals from measured positions before enabling torque, and never changes the gripper. SDK auto-configuration and auto-recalibration are excluded.

Trajectory validation uses analytic quintic extrema plus scheduled targets. It checks joint positions, velocity, acceleration, relative target changes, feedback error, and waypoint/destination settling. It does not prove geometric collision clearance; Phase 4 must validate the full loaded sweep.

The live adapter locally bounds SDK packet waits to 20 ms, disables observation retries, and uses the SDK relative target guard. These limits have not been benchmarked on the physical arm in this phase. SDK clipping faults rather than silently modifying an approved trajectory.

## Stop and fault semantics

Hold cancels and inhibits movement. Stop latches STOPPED. Faults latch FAULT, and underlying fault information survives an operator Stop. Healthy-transport cancellation writes measured arm positions through the same owner; failed/stale feedback or a failed hold is reported unconfirmed. Neither operation changes the gripper or removes torque.

Reset returns to Hold, requires valid feedback/resolved conditions, and never parks or resumes. An interrupted position outside approved anchors remains movement-inhibited. There is no software guarantee of physical braking during blocked/lost serial communication; the tested physical stop remains necessary.
